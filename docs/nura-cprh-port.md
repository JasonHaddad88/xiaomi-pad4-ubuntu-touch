# CPU DVFS for clover: porting the HiBy CPRh + OSM series to 7.0.14

Status 2026-10-30: **built and verified offline; nothing booted yet.**
Background and the data review: `docs/nura-hiby-cprh-review.md`.

## What was done

On a git repository of the exact installed kernel source
(sdm660-mainline `v7.0.14-sdm660`), in order:

1. HiBy `0001` (CPR3/CPRh driver): applied cleanly.
2. **Backport commit**: the 7.2.3 versions of `qcom-cpufreq-hw.c`,
   `Kconfig.arm`, `cpufreq-dt-platdev.c` and the cpufreq-hw binding. Between
   7.0.14 and 7.2.3 these only gained `soc_data->lut_max_entries` (the series
   needs it), one unrelated SoC entry, a Kconfig label and one blocklist line,
   and **lost a real bug**: 7.0.14 does `kfree(data)` where `data` points into
   a `devm_kzalloc`'d array, which corrupts memory when a cpufreq policy is
   torn down.
3. HiBy `0002`-`0014` (OSM programming, bring-up instruments, MSM8998 fixes)
   and `0019`-`0023` (SDM660 CPRh, SDM660 OSM, platdev block, bindings,
   SDM660 L2 SAW AVS fix): all applied cleanly. `0007`/`0008` are needed by
   `0009` even though they look unrelated.
4. **Device tree, without touching any shared SoC file:**
   - `sdm660-cprh-osm.dtsi`: the CPU-DVFS hunks of HiBy `0041`, verbatim (L2
     SAW AVS ports, cpufreq-hw, CPRh, 40 fuse cells, CPRh corners). The idle
     rework, GPU, display and watchdog parts of `0041` are left out: they
     depend on other HiBy patches and are not needed for DVFS.
   - `sda660-xiaomi-clover-cpufreq-bin{0,1,3,4}.dts(i)`: generated by
     `tools/gen-clover-cpufreq-dt.py` from **clover's own** Android OSM
     tables, one per speed bin. Each CPU links to its CPRh thread by the
     `"cpr"` name only; 7.0.14 has no PSCI CPU power domains, so the RS6's
     `"psci"` entry is not needed.
5. **Fail-safe commit**: both bring-up gates default to closed. A boot
   without explicit gate parameters programs nothing.

The 22 resulting patches are in `device-fixes/nura/cpufreq/cprh-osm-port/`.

## Offline verification

- `tools/check-clover-osm-lut.py` simulates the driver's own formula for the
  OSM table words. **55 of 55 rows**, all four bins, give FREQ / OVERRIDE /
  SPARE words identical to clover's Android words.
- No compiler warnings or errors in any ported file.
- Inside the built package: `CONFIG_ARM_QCOM_CPUFREQ_HW=y`,
  `CONFIG_QCOM_CPR3=y`, `CONFIG_QCOM_SPM=y`,
  `CONFIG_MODULE_ALLOW_BTF_MISMATCH=y` (read from the binary's IKCONFIG).
  The drivers must be **built in**, so this kernel never loads the stale
  `qcom-cpufreq-hw.ko` / `spm.ko` from the installed rootfs.
- All four bin DTBs: CPRh, cpufreq-hw and both L2 SAW ports enabled, 8 of 8
  CPUs linked. Top A73 frequency per bin: 2457.6 / 2208 / 1804.8 / 1958.4 MHz.

## The bring-up gates

Command line, built in:

- `qcom_cpr3.cprh_init_stop=N`
  - 0: attach only, **no register access**
  - 1: CPU OPP table
  - 2: every corner computed from the fuses, **still no writes**
  - 3: CPR registers
  - 4: corner table written, but the init then **stops** (`phase >= N`), so the
    thread is never marked initialised. **Full = 5** (corrected after T10)
- `qcom_cpufreq_hw.osm_setup_stop=N`
  - 0: nothing
  - 1: CPRh corner table
  - 2: LUT rows
  - 3: sequencer MEM-ACC/APM through TrustZone
  - 4-7: DCVS policy, boost and droop timers, FSM enable
  - 8-10: ACD (SDM660 has none)
  - 11: OSM enable
  - 12: CPRh follows the OSM, i.e. the full sequence

  Below 11 the OSM stays disabled and cpufreq probing fails cleanly.

## T7 result (2026-10-30): boots clean, but it tested less than intended

T7 (`cprh_init_stop=2`, `osm_setup_stop=0`) booted in ~90 s, and both gates
read back live with the exact values given. Observed:

- `osm-setup: domain N step 0 ok (nothing)` on all 8 CPUs, then a clean
  `-ECANCELED` and normal boot. No register touched.
- `Driver 'qcom_spm' is already registered, aborting`: the stale `spm.ko`
  from the installed rootfs was refused because the patched SPM is built in.
- `179c8000.power-controller` bound to `qcom-cpr3`; nothing deferred.
- Generic `cpufreq-dt` still tried and failed: the blocklist named
  `qcom,sdm660`, but clover's root compatible is `qcom,sda660`. Fixed in the
  next build.

**My test-design mistake:** the CPRh phases only run when OSM step 1
attaches the CPRh domain (`qcom_cpufreq_gen_params()`), so with
`osm_setup_stop=0` the corner computation never started, and `cprh_init_stop=2`
was never exercised. T8 corrects this with `osm_setup_stop=1`. Verified in
the code: step 1 attaches the domain and builds the table in memory; the
first `writel` and the corner request come after step 1's stop check.

**Do not read the raw qfprom block from userspace.** Reading 32 KiB of
`/sys/bus/nvmem/devices/qfprom0/nvmem` took the tablet down (likely a
secure-only fuse row), and a 1-byte read at `0x4133` returned nothing. The
CPR3 driver reads the cells it needs (`cpr_speed_bin`, `cpr_fuse_revision`,
the 38 calibration cells) through nvmem at probe, which worked in T7. The
next build logs the speed bin and fusing revision from there.

## Gate bug found and fixed before T9

On SoCs without ACD (SDM630/660), `qcom_cpufreq_hw_acd_init()` returned 0
**before** its step 8-10 checks, so `osm_setup_stop=8..10` fell through to
the PERF_STATE and **OSM enable** writes and only stopped at step 11. The
gate's own documentation ("any N below 11 leaves the OSM disabled") was false
on clover. Fixed by checking step 10 in the no-ACD path too. Found by reading
the code before building T9, not by booting it.

## Test kernel now defaults to the powersave governor

Built-in `powersave`/`userspace` governors, with `powersave` as default (test
builds only). The governor modules on the rootfs aren't available when the
built-in cpufreq driver registers, so a cmdline `cpufreq.default_governor=`
would silently fall back to schedutil, which jumps straight to full speed.
With powersave, a boot that enables the OSM holds every CPU at 300 MHz until
the speed is raised by hand.

Gates `cprh_init_stop=4`, `osm_setup_stop=10`. On both clusters:

- CPRh phases 0-4 `ok`: CPR registers and the full corner table written
  (e.g. A53 `steps [3]: open-loop 74, floor 64` = 400+74x4 = 696 mV open

- OSM steps 1-7 `ok`, including **step 3, the TrustZone sequencer writes**
  (`Wrote APM Pair: [5-6]`), then `step 10 ok (acd-none)`. That is the new
  check: before the fix this boot would have enabled the OSM.
- **No aborts, no SCM errors, no warnings** anywhere in the boot. No cpufreq
  policy was registered, so the OSM stayed off.

Clocks afterwards (dependent-add; Linux numbers the boot CPU, a Silver core,
as cpu0):

```
cpu0 Silver A53: 1375.0 MHz      cpu1-4 Gold A73: 298.1-298.3 MHz
cpu5-7 Silver A53: 1378 MHz
```

The **Gold cluster moved from 598 to ~298 MHz**, i.e. onto the 300 MHz
GPLL0 alternate source, even though the OSM was never enabled. Silver is
unchanged. Harmless (lower clock at the same voltage) and gone at reboot,
but it means the programming steps already touch the Gold clock mux. Note

## T10 result (2026-10-30): the OSM comes up on clover; my gate value stopped the loop

Gates `cprh_init_stop=4`, `osm_setup_stop=12`. Booted in ~1 min.

- `osm-setup: ... step 11 ok (osm-enable)` on both clusters: **the OSM
  switched on without a crash.** Measured clocks then sat at its lowest
  state, ~300 MHz (Silver 274, Gold 296 MHz under load), stable.
- Step 12 failed: `qcom-cpr3: thread N has no corner table` ->
  `Cannot arm the CPRh loop: -22` -> `Cannot setup the OSM for CPUn: -22`, so
  no cpufreq policy registered and nothing could raise the clock.

**Cause: my gate value.** `cprh_stop_after()` returns `phase >= cprh_init_stop`,
and at phase 4 it returns `-ECANCELED` before the success path sets
`thread->cprh_inited`. So `cprh_init_stop=4` writes the corner table but never
marks the thread initialised. HiBy's own "all phases" default was **5**. The
gate table above is corrected.

Consequence while it ran: OSM enabled, CPRh loop not armed, CPUs held at the
lowest OSM state. Safe (300 MHz needs no more voltage than the boot rail
gives), just slow. Log: `backups/cprh-port-2026-10-30/T10-dmesg.txt`.
